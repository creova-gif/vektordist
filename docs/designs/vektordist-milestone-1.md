## Problem Statement

Most distributed vector databases are opaque black boxes benchmarked only at steady state. Engineers who want to study or demonstrate how sharded HNSW indexing, quorum replication, and failover behave under live traffic either have to deploy multi-node cloud clusters (Qdrant, Milvus) or stitch together toy single-node wrappers.

VektorDist Milestone 1 solves this by delivering a laptop-first, self-contained Rust distributed vector search engine where any engineer can clone the repo, run one command on macOS ARM64 or Linux, launch 5 real OS processes, kill a live node mid-workload, and independently verify that acknowledged writes survived and distributed search recovered.

## What Makes This Cool

One command turns a laptop into an observable distributed vector cluster:

```bash
cargo install --path .
vektordist demo \
  --nodes 5 \
  --vectors 100000 \
  --dimensions 768 \
  --replication-factor 3 \
  --seed 42
```

- **Glass-box live cluster TUI (`ratatui`):** Real-time view of active nodes, shard ownership, search availability, `recall@10`, `p50`/`p95`/`p99` latency, throughput, memory usage, cluster event log, and an independently verified `acknowledged_writes_lost` counter.
- **Interactive chaos keys:** Press `k` to `SIGKILL` a live data node while continuous reads and writes are running, `a` to spawn a replacement node and watch WAL catch-up + replica recovery, and `r` to reset.
- **Honest systems engineering:** Zero-data-loss is backed by real CRC32-checked WAL `fsync` quorum (`W=2` of `RF=3`) and a deterministic write-ID verification ledger, not a cosmetic UI counter.

## Constraints

- **Target hardware:** MacBook (macOS ARM64) and Linux; zero Docker, Kubernetes, or cloud infrastructure required for Milestone 1.
- **Memory budget:** `100,000 x 768 x f32` is ~307 MB raw (~921 MB at `RF=3` across 5 nodes, ~1.15 GB total including HNSW graph links, ~230 MB per process). Fits in RAM without quantization or mmap in M1.
- **First-principles Rust core:** Hand-write exact search, HNSW graph construction/traversal, vector distance kernels, CRC32-checked WAL + crash recovery, consistent-hash shard partitioning, quorum replication, and distributed top-K aggregation. Use established crates for async (`tokio`), RPC (`tonic`/`prost`), CLI (`clap`), hashing/CRC (`crc32fast`), and TUI (`ratatui`).
- **Strict Rust quality gate (from `AGENTS.md` and CI):** `cargo fmt --check`, `cargo clippy -- -D warnings` (with `#![deny(clippy::unwrap_used, clippy::expect_used)]` on production crates, relaxed in `#[cfg(test)]`), `cargo audit`, and `cargo test --workspace` with deterministic tests.
- **Standalone repository:** Zero dependency on FlashStore, EdgeGate, TraceMesh, or other personal projects.
- **Explicit M1 failure-boundary honesty:** M1 uses a single authoritative topology coordinator. Killing any data/replica node is supported and tested; coordinator failover (Raft consensus + epoch fencing) is explicitly documented as unsupported in M1 and scheduled for M2.

## Premises

1. Laptop-first `100k x 768d` at `RF=3` in `f32` (~1.15 GB cluster RAM) is the right M1 proving ground; SQ8 quantization, mmap, multi-tenant `org_id` enforcement, hybrid search, and 10M-vector scale wait for M2-M4.
2. M1 uses one authoritative topology coordinator with explicitly documented single-point-of-failure limits: killing any data/replica node is supported and tested; coordinator HA (Raft + fencing) is deferred to M2.
3. Zero acknowledged write loss means quorum WAL `fsync` (`W=2` of `RF=3`) before returning ack, verified by an automated write-ID ledger (every acknowledged `write_id` must survive `SIGKILL` and replica catch-up; unacknowledged in-flight writes may error or retry).
4. Hand-write the systems core (HNSW, distance kernels, CRC32 WAL, shard ring, quorum replication, top-K merge) and use standard Rust crates for async, transport, CLI, and TUI, with zero coupling to external personal repos.
5. Distribution for M1 is `cargo install --path .` plus GitHub Actions CI (unit + deterministic fault-injection tests) after running `git init` in `vektordist/`; prebuilt GitHub Releases binaries are deferred until after M1.8 passes.

## Approaches Considered

- **Approach A (Minimal Viable — Single-Crate Framed-TCP Monolith):** Ruled out because a custom length-prefixed `bincode`/TCP wire protocol has no schema evolution or SDK path for M4/M5 and weakens crate-level boundaries between core indexing and TUI/orchestration.
- **Approach B (Ideal Architecture — Modular Cargo Workspace + Tonic gRPC + `TopologyStore` Trait):** Chosen. Enforces strict compile-time separation (`vektordist-core` stays pure and benchmarkable), uses Tonic gRPC with checked-in Rust protobuf stubs (no `protoc` required for `cargo install --path .`), and hides M1's single coordinator behind a `TopologyStore` trait ready for M2 Raft.
- **Approach C (Creative / Lateral — Deterministic Simulation Core + Real Process Runner):** Ruled out for M1 because abstracting all async I/O, `fsync`, and timers behind deterministic traits adds heavy upfront Rust trait/lifetime complexity that delays the real 5-process TUI demo.

## Recommended Approach

Adopt **Approach B: Modular Cargo Workspace + Tonic gRPC + `TopologyStore` Trait**.

### Key Architectural Decisions

- **Cargo Packaging (`cargo install --path .`):** Root `Cargo.toml` is a hybrid `[workspace]` + `[package]` (`name = "vektordist"`) that directly owns the CLI/TUI binary (`src/main.rs`, `src/cli/`, `src/tui/`) and depends on the 3 member crates (`vektordist-core`, `vektordist-proto`, `vektordist-cluster`). `cargo install --path .` installs the `vektordist` binary directly with no extra flags.
- **Demo Process Model & Cleanup:** `vektordist demo --nodes 5` runs the M1 coordinator, load generator, write-ID verifier, and `ratatui` TUI **in-process** inside the `vektordist demo` supervisor and spawns **5 real OS child processes** (`vektordist node ...`) on ephemeral/configured localhost ports with isolated WAL directories under a temp root (`/tmp/vektordist-demo-<pid>/`). `vektordist coord` remains available as a standalone subcommand for manual multi-terminal setups. On `r` (Reset), `q` (Quit), or `SIGINT`/`SIGTERM`, the supervisor terminates all tracked child PIDs (`SIGTERM`, escalating to `SIGKILL` after 2s), waits for port release, and cleans up the temp WAL directory (unless `--keep-data` is set).
- **Shard, Direct-to-Primary Routing, `shard_epoch` Fencing & Read/Write Quorums (Shape 2):** Deterministic hash partitioning maps each vector ID to 16 logical shards across 3-5 physical nodes with `RF=3` replicas (1 coordinator-assigned primary + 2 followers), configured from a single `ClusterConfig` owned by the coordinator.
  - **Direct-to-Primary Data Plane:** `ClusterClient` caches `TopologySnapshot(epoch, shards)` and sends writes and searches directly to shard primaries/replicas with `expected_epoch`, refreshing once on `WRONG_EPOCH` or transport errors.
  - **Epoch Fencing:** Every shard assignment carries a monotonic `epoch: u64`. Primaries reject stale-epoch writes with `WRONG_EPOCH(current_epoch)`, and followers reject `ReplicateWal` RPCs with `epoch < local_epoch`.
  - **Live Write Path (`W=2` of `RF=3`):** Writes route directly to the shard primary, which assigns a gap-free monotonic `(shard_id, seq_no, write_id)`, appends a length-prefixed CRC32-checksummed WAL record, calls `sync_data()` (`fsync`), replicates in parallel to both followers, and acknowledges the caller only after `>= 2` replicas (primary + at least 1 follower) confirm durable `fsync` and apply to in-memory HNSW inside one owning `ShardEngine`.
  - **WAL Corruption Policy:** On crash replay, a truncated or corrupt **final** frame (from mid-write `SIGKILL`) is safely truncated with a structured warning while preserving all prior `fsync`ed records; any mid-file CRC32 mismatch followed by further bytes hard-fails with `WalCorruptionError { offset }`.
  - **Initial Demo Seeding Path (Batched `fsync`):** To keep laptop demo startup fast (target `~10-20s` for `100,000 x 768d` at `RF=3` on Apple Silicon instead of minutes of sequential `fsync`s), initial dataset seeding appends in batches of `1,000` vectors per shard WAL with one `fsync` per batch (`~300` total replica `fsync`s). Once seeding finishes, the live continuous writer switches to strict per-write quorum `fsync`.
  - **HNSW Flat Arena & Tombstones:** `vektordist-core` stores shard vectors in a contiguous flat `Vec<f32>` arena (`slot * dim..(slot + 1) * dim`) for LLVM auto-vectorization (ARM NEON / AVX2), guards each of the 16 shards with its own `RwLock<ShardEngine>`, and includes a lightweight tombstone bitset so overwrites, deletes, and idempotent WAL replay never leave duplicate vector IDs in search results.
  - **Wire Encoding & Timeouts:** `vektordist-proto` encodes `f32` slices as packed little-endian `bytes` (parsed into domain types at the gRPC boundary) and enforces explicit per-RPC timeouts (`SearchShard: 200ms`, `ReplicateWal: 500ms`, `Heartbeat: 300ms`, `StreamWal: 10s`).
  - **Read Quorum & Failover Reconciliation:** In steady state, reads execute with `R=1` against any healthy replica (accepting brief eventual consistency on the lagging 3rd follower under `W=2`; read-your-writes queries and the write-ID verifier query the shard primary or `R=2`). When a node is `SIGKILL`ed (detected in `~1.5s` via 3 missed 500ms heartbeats, well under the `5s` target), the coordinator pauses primary promotion for affected shards for one **union/anti-entropy WAL reconciliation pass** across the 2 surviving replicas: both survivors exchange any `seq_no` entries present on one but missing on the other (guaranteed to contain every `W=2` acknowledged write because `W=2` overlaps any 2-of-3 surviving set) before the new primary is promoted with `epoch + 1`. During that brief reconciliation window, reads merge both surviving replicas (`R=2`) so no acknowledged write is invisible.
- **Replica Recovery (`RECOVERING` -> `HEALTHY`) & Under-Quorum Behavior:**
  - **Live Catch-Up Handoff:** Pressing `a` spawns a replacement `vektordist node` process. For each shard assigned to it, the shard primary records a `high_watermark_seq`, streams historical WAL entries up to `high_watermark_seq`, and simultaneously dual-streams incoming live writes into the replacement's catch-up buffer. Once the replacement replays through `high_watermark_seq`, drains its live buffer to `lag == 0`, and finishes rebuilding its local HNSW index, the coordinator atomically transitions it from `RECOVERING` to `HEALTHY`.
  - **Under-Quorum (`< 2` Replicas):** If the user presses `k` again while a shard already has only 2 surviving replicas (dropping it to 1 replica, below `W=2`), the cluster remains online for **read-only search** on the remaining replica, rejects writes to under-quorum shards with an explicit `QUORUM_UNAVAILABLE` error (never falsely acknowledging them, so `acknowledged_writes_lost` stays `0`), and shows a `DEGRADED (under-quorum, reads only)` banner in the TUI until `a` restores quorum.
- **Live Drift-Free `recall@10` Evaluation:** During demo startup, the supervisor precomputes exact brute-force top-10 heaps for a fixed 200-query evaluation set (seeded with `--seed 42`). On every acknowledged live write, the supervisor incrementally updates those 200 exact top-10 heaps (`200 x 768` dot products = `<0.1ms` per write), keeping live `recall@10` accurate without drifting as new vectors arrive.
- **Independent Write-ID Verification:** The load generator records every acknowledged `(write_id, vector_id, shard_id)` in an external verification ledger. After `SIGKILL` and again after replica recovery, a verifier queries surviving replicas by `vector_id` and WAL state to prove `acknowledged_writes_lost == 0`.
- **Zero-`protoc` Build DX:** `vektordist-proto` checks in generated `.rs` files (regenerated via an opt-in `codegen` feature), so `cargo install --path .` works on any MacBook or Linux machine with only the Rust toolchain.

## Open Questions

1. **Exact distance metric default:** Cosine similarity (L2-normalized dot product) vs raw Euclidean L2 as the default for the seeded 100k x 768d synthetic benchmark dataset? (Defaulting to normalized cosine similarity keeps recall@10 behavior closest to real embedding models.)
2. **Shard count tuning for 3-5 local nodes:** Whether 16 logical shards (default) or a configurable `--shards` flag gives the best balance of fan-out latency (`<=50ms` p95) and even replica distribution across both 3-node and 5-node laptop clusters.
